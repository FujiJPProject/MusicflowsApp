# 動作確認手順書

通常開発時の基本疎通確認。Issue #39固有の回帰判定は別記録に分離する。

## 1. 自動化された基本確認

```bash
bash scripts/local/check.sh
bash scripts/local/worker-mode.sh status
bash scripts/local/terraform.sh check
```

OK / FAIL / SKIP を確認する。停止している開発用コンテナは SKIP。Docker自体の状態取得エラーはFAIL。Local WorkerモードではMapping Disabledだけでなく、実際にLocal Workerが稼働していることをpsとジョブ結果で確認する。全体起動では Vite・Spring Boot・API Gateway・CloudFront が応答することを確認する。Terraform check は 0 を期待する。Shell構文・Runtime Configの単体テスト結果とIssue固有の合格基準は [Issue39回帰確認.md](Issue39回帰確認.md) を参照。

## 2. CLIで個別に確認

新しいBashを使用する場合:

```bash
set +eu
source scripts/local/common.sh
require_password
dc --profile worker-local ps -a
dc exec -T postgres pg_isready -U app_user -d music_app
dc exec -T postgres psql -U app_user -d music_app -c 'SELECT 1;'
dc exec -T postgres psql -U app_user -d music_app -c '\dt'
aws_test s3 ls
aws_test s3api head-bucket --bucket music-app-local-files
aws_test s3api head-bucket --bucket music-app-local-frontend
aws_test sqs list-queues
aws_test lambda list-functions --query 'Functions[].{Name:FunctionName,Runtime:Runtime,State:State}' --output table
aws_test lambda list-event-source-mappings --function-name music-app-local-music-job-worker
curl -fsS --max-time 30 http://localhost:8081/api/health
```

期待値: tests/test_jobs、S3 2バケット、music-app-local-music-jobs と DLQ、API/Worker Lambda、Mapping Enabled (lambda) / Disabled (local)、health JSON {"status":"OK"}。

```bash
unset API_BASE_URL DIST_HOST
if API_BASE_URL="$(output runtime_api_url)" && [[ "$API_BASE_URL" == http://localhost:4567/* ]]; then
  curl -fsS --max-time 60 "$API_BASE_URL/api/health"
fi
if DIST_HOST="$(dist_host)"; then
  curl -fsS --max-time 30 "http://$DIST_HOST:4567/" >/dev/null
  curl -fsS --max-time 30 "http://$DIST_HOST:4567/jobtest" >/dev/null

```

## 3. ブラウザ

- http://localhost:5174/ と check.sh で表示されたCloudFront URLを開く。
- /dev/db-test: Spring Boot直接を選択し登録・一覧取得。Lambda経由はCognitoにログインして同様に確認。
- /auth-test: ログイン前の保護API拒否、Cognitoログイン、/api/auth/me、DB登録・取得。
- /jobtest: Lambdaモードでログインしジョブを登録。COMPLETED / LAMBDA を確認。
- worker-mode.sh local で切替後、Spring Boot直接でジョブを登録。COMPLETED / LOCAL_WORKER を確認。
- Vite・CloudFrontで同じ操作を繰り返し、SPA直接アクセス・再読込・CORSを確認する。登録したジョブは同じAPI経路・所有者で取得する。

## 4. 明示的なDB書込み確認

診断APIが有効なLocal環境でのみ実行する。データが追加される。

```bash
curl -sS -i -X POST http://localhost:8081/api/tests -H 'Content-Type: application/json' --data '{"name":"Local development test"}'
curl -sS -i http://localhost:8081/api/tests
```

POST 201、GET 200 と登録データを期待する。Lambda経由のBearer認証、他ユーザーのジョブ取得拒否、S3結果の存在は診断画面とAWS CLIを用いて確認する。Tokenを履歴・ログ・コミットに含めない。

## 5. CORS

Vite Origin とCloudFront Originの両方から API Gateway / Spring Boot へ OPTIONS を送信し、許可OriginとAuthorization/Content-Typeヘッダーを確認する。許可していないOriginが許可されないことも確認する。HTTP 502 が発生した場合はトラブルシューティングへ。

## 6. Cognito・API Lambda経由のCLI回帰確認

以下は診断フラグが有効なLocal環境のみ。初めに新しいBashで接続設定を取得する。パスワードは非表示入力し、Tokenをターミナルに表示しない。実AWSへの接続にはこのコマンドを使用しない。

```bash
set +eu
source scripts/local/common.sh
require_password
API_BASE_URL="$(output runtime_api_url)"
CLIENT_ID="$(output runtime_client_id)"
```

API_BASE_URLが http://localhost:4567/ で始まり、CLIENT_IDが有効な場合のみ実行する。既存Cognito開発ユーザーで認証する。

```bash
unset ACCESS_TOKEN
read -r -p 'Cognito username: ' COGNITO_USERNAME
read -rs -p 'Cognito password: ' COGNITO_PASSWORD; echo
if [[ "$API_BASE_URL" == http://localhost:4567/* && -n "$CLIENT_ID" && -n "$COGNITO_USERNAME" && -n "$COGNITO_PASSWORD" ]]; then
  if ACCESS_TOKEN="$(
    set -o pipefail
    printf '%s\n%s\n%s\n' "$CLIENT_ID" "$COGNITO_USERNAME" "$COGNITO_PASSWORD" |
      dc exec -T floci python3 -c 'import json,sys; c,u,p=sys.stdin.read().splitlines(); print(json.dumps(dict(AuthFlow="USER_PASSWORD_AUTH",ClientId=c,AuthParameters=dict(USERNAME=u,PASSWORD=p))))' |
      aws_test cognito-idp initiate-auth --cli-input-json file:///dev/stdin --query AuthenticationResult.AccessToken --output text
  )" && [[ -n "$ACCESS_TOKEN" && "$ACCESS_TOKEN" != None && "$ACCESS_TOKEN" != null ]]; then
    echo 'Access Token取得成功'
  else
    unset ACCESS_TOKEN
    echo 'Access Token取得失敗。後続処理を実行しないでください。'
  fi
fi
unset COGNITO_PASSWORD
```

認証なしで /api/auth/me を呼び出して拒否されること、認証ありで200を返すことを確認する。Authorizationをプロセス引数に直接渡さない。

```bash
curl -sS -i --max-time 60 "$API_BASE_URL/api/auth/me"
if [[ "$API_BASE_URL" == http://localhost:4567/* && -n "${ACCESS_TOKEN:-}" ]]; then
  printf 'header = "Authorization: Bearer %s"\n' "$ACCESS_TOKEN" |
    curl -sS -i --max-time 60 --config - "$API_BASE_URL/api/auth/me"
fi
```

DB疎通確認（Lambda経由、データが追加される）:

```bash
if [[ "$API_BASE_URL" == http://localhost:4567/* && -n "${ACCESS_TOKEN:-}" ]]; then
  printf 'header = "Authorization: Bearer %s"\n' "$ACCESS_TOKEN" |
    curl -sS -i --max-time 60 --config - -X POST "$API_BASE_URL/api/tests" -H 'Content-Type: application/json' --data '{"name":"Lambda DB regression"}'
  printf 'header = "Authorization: Bearer %s"\n' "$ACCESS_TOKEN" |
    curl -sS -i --max-time 60 --config - "$API_BASE_URL/api/tests"
fi
```

POST 201・GET 200を期待する。Lambdaモードでジョブを登録する。

```bash
if [[ "$API_BASE_URL" == http://localhost:4567/* && -n "${ACCESS_TOKEN:-}" ]]; then
  printf 'header = "Authorization: Bearer %s"\n' "$ACCESS_TOKEN" |
    curl -sS -i --max-time 60 --config - -X POST "$API_BASE_URL/api/test-jobs" -H 'Content-Type: application/json' --data '{"payload":"Local development job"}'
fi
```

HTTP 202、status=QUEUED、jobId、resultKeyを確認する。生成されたjobIdを入力する。

```bash
read -r -p 'Job ID: ' JOB_ID
if [[ "$JOB_ID" =~ ^[0-9a-fA-F-]{36}$ && "$API_BASE_URL" == http://localhost:4567/* && -n "${ACCESS_TOKEN:-}" ]]; then
  printf 'header = "Authorization: Bearer %s"\n' "$ACCESS_TOKEN" |
    curl -sS -i --max-time 60 --config - "$API_BASE_URL/api/test-jobs/$JOB_ID/result"
  aws_test s3api head-object --bucket music-app-local-files --key "worker-results/$JOB_ID.json"
fi
```

処理中は202、完了後は200・COMPLETED・processorType=LAMBDA。S3は完了後に存在する。異なるCognitoユーザーで取得した場合は拒否されることを確認する。Tokenを使い終えたら `unset ACCESS_TOKEN`。

## 7. Local Worker・SQS・CORSのCLI確認

```bash
bash scripts/local/worker-mode.sh local
bash scripts/local/start.sh worker-local
bash scripts/local/worker-mode.sh status
```

新規ジョブ停止と切替成功を確認してから実行する。

```bash
curl -sS -i --max-time 30 -X POST http://localhost:8081/api/test-jobs -H 'Content-Type: application/json' --data '{"payload":"Local worker regression"}'
read -r -p 'Job ID: ' JOB_ID
if [[ "$JOB_ID" =~ ^[0-9a-fA-F-]{36}$ ]]; then
  curl -sS -i --max-time 30 "http://localhost:8081/api/test-jobs/$JOB_ID/result"
  aws_test s3api head-object --bucket music-app-local-files --key "worker-results/$JOB_ID.json"
fi
```

COMPLETED・LOCAL_WORKERを期待する。登録時と同じAPI経路・所有者で結果を取得する。

```bash
JOB_QUEUE_URL="$(output job_queue_url)"
DLQ_URL="$(output dlq_url)"
if [[ -n "$JOB_QUEUE_URL" && -n "$DLQ_URL" ]]; then
  aws_test sqs get-queue-attributes --queue-url "$JOB_QUEUE_URL" --attribute-names VisibilityTimeout MessageRetentionPeriod RedrivePolicy
  aws_test sqs get-queue-attributes --queue-url "$DLQ_URL" --attribute-names MessageRetentionPeriod
fi
```

期待値: VisibilityTimeout=180、MessageRetentionPeriod=345600、RedrivePolicyのmaxReceiveCount=5、DLQ保持期間1209600。DLQへの実配送テストは専用検証データで実施し、通常開発データをpurgeしない。

CORSはAPI Gatewayと直接Backend、ViteとCloudFrontの両Originの組合せを確認する。

```bash
API_BASE_URL="$(output runtime_api_url)"
if DIST_HOST="$(dist_host)" && [[ "$API_BASE_URL" == http://localhost:4567/* ]]; then
  for endpoint in "$API_BASE_URL/api/tests" http://localhost:8081/api/tests; do
    for origin in http://localhost:5174 "http://$DIST_HOST:4567" http://unapproved.invalid; do
      curl -sS -i --max-time 60 -X OPTIONS "$endpoint" -H "Origin: $origin" -H 'Access-Control-Request-Method: GET' -H 'Access-Control-Request-Headers: authorization,content-type'
    done
  done
fi
```

許可されたOriginでプリフライトが成功し、対応するAccess-Control-Allow-Originとヘッダーが返ること、未許可Originにはアクセス許可が返らないことを確認する。終了後は必要なWorkerモードに戻す。

```bash
unset API_BASE_URL CLIENT_ID JOB_ID JOB_QUEUE_URL DLQ_URL DIST_HOST COGNITO_USERNAME ACCESS_TOKEN TEST_DB_PASSWORD
```
